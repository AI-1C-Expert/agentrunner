================================================================================
  РАЗРАБОТКА СВОЕГО TOOL ДЛЯ AgentRunner
  Руководство для разработчиков команды / партнёров
================================================================================

Аудитория: BSL-разработчик (внедренец, партнёр), умеющий писать код 1С и
работать с расширениями конфигурации, но не знакомый с внутренним устройством
AgentRunner. Термины проекта (RunId, ActionPayload, approval-очередь и т. п.)
объясняются по ходу текста.

ВАЖНО ДЛЯ СОПРОВОЖДЕНИЯ: этот текст — копия внутреннего руководства, встроенная
в расширение как общий макет ar_Инструкция_РазработкаTool, чтобы разработчик мог
прочитать её прямо из конфигуратора/предприятия, не имея доступа к репозиторию
ядра. При любом изменении контракта tool-функций, диспетчера тулов или процесса
регистрации ЭТОТ МАКЕТ НУЖНО АКТУАЛИЗИРОВАТЬ вместе с исходным документом.


================================================================================
  1. ЗАЧЕМ ЭТОТ ДОКУМЕНТ
================================================================================

Если конфигурации, на которой вы внедряете AgentRunner, не хватает встроенных
tools — ПИШИТЕ СВОЙ TOOL КАК ЧАСТЬ СВОЕГО ОВЕРЛЕЯ src/, а не правьте ядровые
tool-модули напрямую.

AgentRunner сам является расширением конфигурации. В 1С расширение может
заимствовать и патчить объекты только основной конфигурации — не другое
расширение («расширение поверх расширения» физически не работает). Поэтому свой
tool не устанавливается как отдельный плагин-`.cfe` поверх готового
AgentRunner.cfe — это часть сборки самого расширения: ваша копия src/ (форк/
оверлей), где вы правите РОВНО ОДИН ядровой файл — общий модуль
ar_ToolПереопределяемый — и добавляете свои собственные общие модули рядом с
ним. Готовый .cfe компилируется из этой объединённой копии src/.

Это не патч ядра форком в худшем смысле: вы не трогаете диспетчер
(ar_ToolDispatcher), permission engine, approval-очередь и остальную логику
ядра — только предусмотренную точку расширения (ar_ToolПереопределяемый), по
тому же принципу, что БСП-модули …Переопределяемый (ОбщегоНазначенияПереопределяемый
и т. п.), которые кастомизируются в конкретной конфигурации-потребителе.

Этот документ даёт полный путь «от нуля до работающего своего tool» через
предусмотренную точку расширения ядра — ar_ToolПереопределяемый.


================================================================================
  2. СЛОИ: УНИВЕРСАЛЬНЫЙ vs ПРЕДМЕТНЫЙ
================================================================================

Блок tools AgentRunner состоит из слоёв с разной переносимостью между
конфигурациями (типовая, БП, УТ, ERP, отраслевая):

  УНИВЕРСАЛЬНЫЙ СЛОЙ
    Модули-примеры : ar_ToolUniversal (query, aggregate, get_object,
                     search_metadata, ...)
    Переносимость  : высокая — работает на любой конфигурации без адаптации.
    Почему         : уже метаданно-нейтральный. Имена таблиц/полей приходят из
                     Метаданные.*, применяется whitelist полей, нет зашитых имён
                     реквизитов.

  ПРЕДМЕТНЫЙ СЛОЙ, ЧТЕНИЕ
    Пример         : «получить счёт», «поиск клиентов».
    Переносимость  : средняя — чинится маппингом имён реквизитов.
    Чем решается   : ar_МаппингМетаданных / профиль конфигурации.

  ПРЕДМЕТНЫЙ СЛОЙ, ЗАПИСЬ
    Пример         : «создать черновик счёта» (create_invoice_draft).
    Переносимость  : низкая — маппинг не решает.
    Чем решается   : ar_АдаптерЗаполнения — нужна выделенная реализация под
                     конкретную конфигурацию.

Причина разного ранга для чтения и записи: чтение сводится к «как называется
поле» — этого достаточно, чтобы построить ВЫБРАТЬ. Запись типового документа —
это родной механизм конфигурации (Заполнить() -> ОбработкаЗаполнения ->
функциональные опции, учётная политика, десятки связанных полей), который НЕ
сводится к присваиванию реквизитов и который маппинг имён не решает и не должен
решать.

ПРАВИЛО, КОТОРОЕ НУЖНО ЗАПОМНИТЬ ПРЕЖДЕ ВСЕГО ОСТАЛЬНОГО:

    Свой tool под конкретную конфигурацию = свой общий модуль в вашем
    оверлее src/ + одна ветвь в ar_ToolПереопределяемый, а НЕ произвольная
    правка ar_ToolDispatcher/ar_ToolCRM и других ядровых модулей.

Код распространяется как часть собранного .cfe — осознанная административная
установка расширения с полным аудитом средствами платформы, — а не через режим
«Код» (см. раздел 7 ниже).


================================================================================
  3. КОНТРАКТ TOOL-ФУНКЦИИ
================================================================================

Любая tool-функция — универсальная, предметного чтения или предметной записи —
обязана соблюдать единую сигнатуру и набор правил.

------------------------------------------------------------------- 3.1. Сигнатура

    Функция ИмяTool(Знач АргументыJSON, Знач КонтекстЗапуска = Неопределено) Экспорт

  - АргументыJSON (Строка) — JSON-объект аргументов, пришедших от LLM (плюс
    системные поля _dry_run / _idempotency_key, которые диспетчер подмешивает в
    аргументы автоматически).
  - КонтекстЗапуска (Структура, может быть Неопределено) — контекст запуска:
    RunId (идентификатор текущего прогона агента), Sequence, ссылка на агента
    и т. п.
  - Возврат — СТРОКА, JSON-observation, которая добавляется в контекст диалога
    как role: tool (то, что «увидит» модель в ответ на вызов инструмента).

------------------------------- 3.2. Диспетчер не выбрасывает исключений наружу

Любая ошибка tool превращается в JSON вида {"error":"<код>"}, а НЕ в
необработанное исключение. Точка входа функции не должна пробрасывать исключение
наружу диспетчера — модель должна получить текстовую ошибку и иметь шанс
скорректировать следующий вызов, а не оборвать цикл рассуждения.

--------------- 3.3. Контракт для mutating tools (RiskLevel: Draft/Write/Commit)

Если ваш tool НЕ ТОЛЬКО ЧИТАЕТ, а создаёт/меняет данные, он обязан:

1. ПРОВЕРИТЬ DryRun В НАЧАЛЕ ФУНКЦИИ.

     Если ar_ToolDispatcher.ИзвлечьDryRun(АргументыJSON) Тогда
         Возврат ar_ToolDispatcher.СформироватьDryRunJSON("<имя_tool>", СимулированныеДанные);
     КонецЕсли;

   ИзвлечьDryRun возвращает Истина ТОЛЬКО при булевом true в поле _dry_run
   (защитный дефолт — Ложь: безопаснее выполнить реально, чем случайно пропустить
   операцию). СформироватьDryRunJSON формирует единый ответ
   {"dry_run": true, "tool": "<имя>", "simulated": <данные>} БЕЗ ЗАПИСИ В ИБ.

2. ДЛЯ ТулаС ТРЕБУЕТApproval = Истина — ПРОЧИТАТЬ _idempotency_key через
   ar_ToolDispatcher.ИзвлечьIdempotencyKey(АргументыJSON). После подтверждения
   оператором диспетчер сам ищет кэш по этому ключу — свой tool не обязан
   дублировать эту проверку, но может (defence-in-depth).

3. СТРОИТЬ payload И СТАВИТЬ ЕГО В ОЧЕРЕДЬ APPROVAL — НЕ ЗАПИСЫВАТЬ В ИБ НАПРЯМУЮ.
   Mutating tool собирает структуру Действие и ставит её в очередь подтверждений:

     Действие = Новый Структура;
     Действие.Вставить("Имя", "<имя_tool>");
     Действие.Вставить("ИдВызова", ИдВызова);
     Действие.Вставить("Аргументы", Аргументы);
     Действие.Вставить("IdempotencyKey", Ключ);       // опционально
     Действие.Вставить("Обоснование", Обоснование);   // опционально
     Действие.Вставить("RiskLevel", "Draft");         // опционально

     ApprovalId = ar_Approval.Поставить(КонтекстЗапуска, Действие);

   где КонтекстЗапуска обязан содержать непустой RunId, а Действие — структуру
   {Имя, ИдВызова, Аргументы, [IdempotencyKey], [Обоснование], [RiskLevel]}.

   КЛЮЧЕВОЕ ПРАВИЛО: документ/объект НЕ создаётся и НЕ записывается внутри самого
   tool. Реальная запись происходит позже, отдельным исполнителем, который
   вызывается уже ПОСЛЕ подтверждения оператором (ar_Approval.Принять). Паттерн:
   одна функция строит payload и ставит его в очередь; парная функция-исполнитель
   выполняет реальную запись и вызывается очередью после подтверждения.

Для read-only tools весь пункт 3.3 не применяется.

--------------------------------------------- 3.4. Read-only tools и _dry_run

Read-only функции ИГНОРИРУЮТ флаг _dry_run — чтение данных в dry-run безопасно по
определению, дополнительной проверки не требуется.


================================================================================
  4. КАК ПОДКЛЮЧИТЬ СВОЙ TOOL К ДИСПЕТЧЕРУ ЧЕРЕЗ ar_ToolПереопределяемый
================================================================================

Ядро AgentRunner содержит общий модуль ar_ToolПереопределяемый — предусмотренную
точку расширения (тот же БСП-паттерн, что ОбщегоНазначенияПереопределяемый или
ПодключаемыеКомандыПереопределяемый в БСП: пустой по умолчанию модуль, который
прикладной разработчик дополняет в своей копии конфигурации).

Диспетчер (ar_ToolDispatcher.ВыполнитьЯдровойМодуль) для ЛЮБОГО модуля, не
совпавшего ни с одной ядровой веткой (ar_ToolCRM, ar_ToolUniversal и т. п.),
делегирует вызов в ar_ToolПереопределяемый.ВызватьПользовательскийТул — вы НЕ
трогаете ar_ToolDispatcher вообще, только ar_ToolПереопределяемый.

Если вы заведёте запись в справочнике ar_Tools, но не допишете ветвь в
ar_ToolПереопределяемый, — при вызове модель получит {"error":"unknown_module"}.

--------------------------------------------------- 4.1. Точка добавления в ядре

Внутри тела ВызватьПользовательскийТул (общий модуль ar_ToolПереопределяемый)
есть явный маркер-комментарий:

  // !!! ДОБАВЛЯТЬ НОВУЮ ВЕТВЬ ПОЛЬЗОВАТЕЛЬСКОГО TOOL-МОДУЛЯ ЗДЕСЬ ...

Это единственный ядровой файл, который вы правите — напрямую, в своей копии
src/CommonModules/ar_ToolПереопределяемый/, без каких-либо скиллов cfe-borrow/
cfe-patch-method (они относятся к устаревшей, физически нереализуемой схеме
«расширение поверх расширения» и в актуальной архитектуре не используются).

ВАЖНОЕ ПРАВИЛО ИМЕНОВАНИЯ: имя вашего общего модуля НЕ ДОЛЖНО начинаться с
"ar_" — этот префикс зарезервирован за ядром AgentRunner. Используйте префикс
своей организации/проекта (например "Свой_ToolСклад", "ВашПрефикс_ToolСклад").

--------------------------------------------------- 4.2. Практические шаги

1. Создайте свой общий модуль (например ВашПрефикс_ToolСклад) в своей копии
   src/CommonModules/ — Skill(meta-compile) (Сервер, без вызова с клиента, без
   привилегированного режима). Модуль содержит экспортную функцию Диспетчер —
   двухуровневое ветвление по имени процедуры, тем же паттерном, что ядровые
   ar_ToolДокументы.Диспетчер и др.:

     Функция Диспетчер(Знач ИмяПроцедуры, Знач Аргументы, Знач Контекст) Экспорт
         Если ИмяПроцедуры = "ПолучитьОстатокСклада" Тогда
             Возврат ПолучитьОстатокСклада(Аргументы, Контекст);
         Иначе
             Возврат ОшибочныйJSON("unknown_procedure");
         КонецЕсли;
     КонецФункции

   Тоже без Выполнить()/Вычислить() — двухуровневое ветвление держится
   сравнением строк (Если/ИначеЕсли), а не динамическим вызовом по имени.

2. Откройте ar_ToolПереопределяемый.bsl и допишите ОДНУ ветвь в
   ВызватьПользовательскийТул перед маркером-комментарием:

     ИначеЕсли ИмяМодуля = "ВашПрефикс_ToolСклад" Тогда
         Возврат ВашПрефикс_ToolСклад.Диспетчер(ИмяПроцедуры, Аргументы, Контекст);

   Строка-имя модуля ("ВашПрефикс_ToolСклад") ОБЯЗАНА совпадать с реальным именем
   файла общего модуля из шага 1 и со значением ar_ОбщийМодуль, которое вы
   запишете в справочник ar_Tools при регистрации (см. 4.3). Несколько
   независимых доработок сосуществуют без конфликтов — просто несколько ветвей
   ИначеЕсли подряд, по одной на модуль.

3. В той же процедуре ПриФормированииСпискаМодулейТулов допишите регистрацию
   имени вашего модуля — для диагностики согласованности списка и ветвления:

     Модули.Добавить("ВашПрефикс_ToolСклад");

------------------------------------------- 4.3. Регистрация в справочнике ar_Tools

Регистрация — программная. Обязательные поля записи:

  ar_Имя            Имя tool для LLM, snake_case (например get_warehouse_stock).
  ar_ОбщийМодуль    Имя вашего общего модуля — должно совпадать с именем файла и
                    с веткой ИначеЕсли из 4.2.
  ar_ИмяПроцедуры   Имя экспортной функции второго уровня.
  ar_ТипРеализации  "Процедура" (пустая строка = «Процедура» по умолчанию; режим
                    «Код» не подходит для распространяемого tool — см. раздел 7).
  ar_RiskLevel      Элемент Перечисления.ar_RiskLevel: Read / Draft / Write / Commit.
  ar_ТребуетApproval  Ложь для read-only, Истина для mutating.
  ar_JSONManifest   JSON Schema аргументов, обёрнутая в OpenAI tool-format.
  ar_ИсточникРасширение  Осмысленное имя вашего комплекта доработок (не имя
                    отдельного .cfe — плагин-расширения не будет, ваш tool
                    собирается в составе единого AgentRunner.cfe).
  ar_ТребуемыеОбъекты  JSON-массив логических имён объектов метаданных, без
                    которых tool не может работать (см. раздел 5).
  ar_Включён        Истина.

Регистрационная функция может вызываться либо из собственного обработчика
обновления, который вы добавляете в свою копию src/ (ar_ОбновлениеРасширения —
так же, как ядро регистрирует свои встроенные tools), либо из любого другого
кода инициализации вашей сборки. Ядро само не вызывает ЗарегистрироватьTools()
пользовательских модулей по имени (это потребовало бы Выполнить() — запрещено
правилом проекта) — регистрация всегда явная, на стороне разработчика.


================================================================================
  5. ПРАВИЛА УНИВЕРСАЛЬНОСТИ
================================================================================

Если вы хотите, чтобы ваш tool работал не только на одной конкретной базе, а был
переносим между конфигурациями (или просто переживал переименование объектов на
той же базе) — соблюдайте:

1. ИМЕНА ОБЪЕКТОВ МЕТАДАННЫХ — ТОЛЬКО ЧЕРЕЗ INDIRECTION, никогда не текстом
   напрямую:

     ИмяРегистра = ar_ToolDispatcher.ИмяОбъектаМетаданных("ОстаткиНоменклатуры", "ТоварыНаСкладах");

   Сигнатура:
     Функция ИмяОбъектаМетаданных(Знач ЛогическоеИмя, Знач ИмяПоУмолчанию) Экспорт

   Источник переопределений — регистр сведений ar_ПереопределенияОбъектов.
   Приоритет: если для ЛогическоеИмя есть запись в регистре — используется она,
   иначе — ИмяПоУмолчанию.

2. ИМЕНА РЕКВИЗИТОВ ПРИ ЧТЕНИИ — ТОЛЬКО ЧЕРЕЗ ar_МаппингМетаданных.ИмяРеквизита:

     ИмяРеквизита = ar_МаппингМетаданных.ИмяРеквизита("invoice.total_attribute", "СуммаДокумента");

   Сигнатура:
     Функция ИмяРеквизита(Знач ЛогическийКлюч, Знач ИмяПоУмолчанию) Экспорт

   Источник — профиль конфигурации.

   ГРАНИЦА: этот механизм — ТОЛЬКО ДЛЯ ОПЕРАЦИЙ ЧТЕНИЯ. Заполнение документов
   (запись) идёт через ar_АдаптерЗаполнения, не через маппинг реквизитов — см.
   раздел 6. Знание «поле называется так-то» не решает задачу корректного
   заполнения типового документа.

3. ПЕРЕД ОБРАЩЕНИЕМ К РЕКВИЗИТУ В ЗАПРОСЕ — ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА НАЛИЧИЯ:

     Есть = МД.Реквизиты.Найти(ИмяРеквизита) <> Неопределено;

   Поля запроса собираются динамически по результату проверки: реквизит
   добавляется в текст ВЫБРАТЬ, только если он реально есть в метаданных, а для
   отсутствующих — пишется предупреждение (см. следующий пункт).

4. ОТСУТСТВУЮЩИЙ РЕКВИЗИТ/ОБЪЕКТ -> warnings, А НЕ error И НЕ ИСКЛЮЧЕНИЕ. LLM
   должен получить частичный, но полезный результат, а не отказ. Формат:

     "attribute_not_available:<логический_ключ>:<фактическое_имя>"

   Например:
     Предупреждения.Добавить("attribute_not_available:" + ЛогическийКлюч + ":" + ИмяРеквизита);

5. СВОЕМУ TOOL-У ОБЯЗАТЕЛЬНО ЗАПОЛНЯТЬ ar_ТребуемыеОбъекты ПРИ РЕГИСТРАЦИИ. Это
   массив логических имён объектов метаданных, без которых tool не может
   отработать. Без этого поля tool будет предложен LLM даже на конфигурациях, где
   он физически не сработает — модель потратит вызов впустую и получит структурную
   ошибку вместо осмысленного {"error": "..."}. Доступность tool проверяется
   диспетчером и кэшируется в поле ar_Доступен справочника ar_Tools.


================================================================================
  6. КОГДА НУЖЕН АДАПТЕР ЗАПОЛНЕНИЯ, А НЕ МАППИНГ РЕКВИЗИТОВ
================================================================================

Если ваш tool СОЗДАЁТ ИЛИ МЕНЯЕТ типовой документ конфигурации — маппинга имён
реквизитов (раздел 5, пункт 2) НЕДОСТАТОЧНО. Ещё раз явно: ar_МаппингМетаданных —
только для чтения. Это тот момент, который легко упустить, увидев работающий
пример чтения и по аналогии применив тот же подход к записи.

Для записи нужен контракт ar_АдаптерЗаполнения:

  - ПоддерживаемыеКонфигурации() — какие конфигурации адаптер обслуживает;
  - ТребуемыеОбъекты()          — аналогично ar_ТребуемыеОбъекты в ar_Tools;
  - СоздатьЧерновик<Документ>(Payload, Отказ, Сообщения) — собственно заполнение.

Точка расширения — маркер «// !!! ДОБАВЛЯТЬ НОВЫЙ АДАПТЕР ЗДЕСЬ» в функции
ar_АдаптерЗаполнения.ВызватьАдаптер.

ПРАВИЛО, КРИТИЧНОЕ ДЛЯ ПОРЯДКА ВЫЗОВОВ: родной Заполнить() документа вызывается
ДО присваивания прикладных полей payload'а, иначе типовой механизм заполнения их
затрёт; ПроверитьЗаполнение() обязателен перед возвратом из адаптера.

Это отдельная, более сложная тема со своим примером — за образцом полной
реализации адаптера обратитесь к сопровождающему ядра AgentRunner.


================================================================================
  7. РЕЖИМ «КОД» — НЕ ДЛЯ РАСПРОСТРАНЯЕМЫХ TOOLS
================================================================================

В справочнике ar_Tools есть второй режим реализации tool — ar_ТипРеализации =
"Код", при котором произвольный BSL из поля ar_КодРеализации исполняется
диспетчером через Выполнить() под УстановитьБезопасныйРежим. Он существует ДЛЯ
ЛОКАЛЬНЫХ AD HOC TOOLS, вводимых администратором вручную прямо в карточке
ar_Tools — быстрый эксперимент без правки общих модулей.

Режим огорожен константой ar_РазрешитьТулыВРежимеКод (Булево, ПО УМОЛЧАНИЮ ЛОЖЬ) —
при Ложь диспетчер отдаёт контракт {"error":"tool_disabled_or_not_found"} без
падения ядра.

ДЛЯ РАСПРОСТРАНЯЕМОГО, ВЕРСИОНИРУЕМОГО, ТЕСТИРУЕМОГО TOOL-А РЕЖИМ «КОД» —
НЕПОДХОДЯЩИЙ ПУТЬ: нет статического анализа, нет истории в git, нет ревью.
Безопасный режим платформы (УстановитьБезопасныйРежим) НЕ БЛОКИРУЕТ:

  - чтение любых данных, доступных пользователю текущей сессии (tools исполняются
    в правах пользователя, чтобы RLS работал естественно — это же означает, что
    произвольный код видит всё, что видит пользователь);
  - запись в ИБ в обход очереди подтверждений (Записать() и
    ЗафиксироватьТранзакцию() можно вызвать напрямую; весь approval-контракт
    держится на дисциплине кода в режиме «Процедура», а не на техническом
    ограничении платформы);
  - исходящие HTTP-соединения (то есть эксфильтрацию данных на внешний адрес).

РЕКОМЕНДАЦИЯ: ВСЕГДА РЕЖИМ «ПРОЦЕДУРА» + СВОЙ ОБЩИЙ МОДУЛЬ ЧЕРЕЗ
ar_ToolПереопределяемый. Режим «Код» — только для быстрых локальных
экспериментов на своей базе, никогда для tools, которые вы собираетесь
распространять/выкладывать в сообщество.


================================================================================
  8. ПОЛНЫЙ ПРИМЕР: get_warehouse_stock
================================================================================

Walkthrough «от нуля до вызова» на примере read-only tool, отдающего остаток
номенклатуры на складе через виртуальную таблицу РегистрНакопления.Остатки.

Почему именно этот пример: он read-only (RiskLevel = Read,
ar_ТребуетApproval = Ложь) — не требует объяснения approval-очереди и адаптера
заполнения, но при этом достаточно нетривиален, чтобы показать реальные правила
универсальности из раздела 5 (ИмяОбъектаМетаданных, проверка наличия перед
обращением, warnings вместо error).

------------------------------------ Шаг 1. Общий модуль ВашПрефикс_ToolСклад

В своей копии src/CommonModules/ создайте новый общий модуль (в примерах ниже —
ВашПрефикс_ToolСклад, префикс "ВашПрефикс_" — НЕ "ar_", см. правило именования
из раздела 4.1) — Skill(meta-compile), свойства: Сервер, без вызова с клиента,
без привилегированного режима.

Полный код функции ПолучитьОстатокСклада (реалистичный минимальный пример,
компилируемый BSL):

// Общий модуль ВашПрефикс_ToolСклад (серверный, без вызова с клиента).
//
// Tool get_warehouse_stock: остаток номенклатуры на складе через виртуальную
// таблицу РегистрНакопления.Остатки. RiskLevel = Read, ar_ТребуетApproval = Ложь,
// _dry_run не проверяется (чтение в dry-run безопасно).
//
// Формат возвращаемого JSON:
//  успех: {"nomenclature":"<нав.ссылка>","warehouse":"<нав.ссылка>","quantity":N,"warnings":[...]}
//  ошибка: {"error":"<код>","warnings":[...]}
//
// Параметры:
//  АргументыJSON   - Строка    - JSON вида {"nomenclature_ref": "...", "warehouse_ref": "..."}.
//                    nomenclature_ref/warehouse_ref - навигационная ссылка вида
//                    "e1cib/data/<Класс>.<Объект>?ref=<GUID>" (формат, который
//                    принимает ar_Утилиты.ОбъектИзНавигационнойСсылки), не
//                    произвольный UUID и не "голая" строка идентификатора.
//  КонтекстЗапуска - Структура - КонтекстЗапуска. Может быть Неопределено.
//
// Возвращаемое значение:
//  Строка - JSON-observation, см. раздел "Формат возвращаемого JSON" выше.
//
Функция ПолучитьОстатокСклада(Знач АргументыJSON, Знач КонтекстЗапуска = Неопределено) Экспорт

	Предупреждения = Новый Массив;

	// 1. Десериализация аргументов.
	Аргументы = ДесериализоватьАргументыСклад(АргументыJSON);
	Если Аргументы = Неопределено Тогда
		Возврат ОшибкаСклад("invalid_json_arguments", Предупреждения);
	КонецЕсли;

	СтрокаНоменклатуры = СокрЛП(Строка(ЗначениеИзКоллекцииСклад(Аргументы, "nomenclature_ref", "")));
	СтрокаСклада = СокрЛП(Строка(ЗначениеИзКоллекцииСклад(Аргументы, "warehouse_ref", "")));

	Если ПустаяСтрока(СтрокаНоменклатуры) Тогда
		Возврат ОшибкаСклад("nomenclature_ref is required", Предупреждения);
	КонецЕсли;
	Если ПустаяСтрока(СтрокаСклада) Тогда
		Возврат ОшибкаСклад("warehouse_ref is required", Предупреждения);
	КонецЕсли;

	// 2. Indirection имени объекта метаданных: логическое имя "ОстаткиНоменклатуры"
	// превращается в "ТоварыНаСкладах" по умолчанию, переопределяется регистром
	// ar_ПереопределенияОбъектов на целевой конфигурации.
	ИмяРегистра = ar_ToolDispatcher.ИмяОбъектаМетаданных("ОстаткиНоменклатуры", "ТоварыНаСкладах");

	МДРегистр = Метаданные.РегистрыНакопления.Найти(ИмяРегистра);
	Если МДРегистр = Неопределено Тогда
		Предупреждения.Добавить("attribute_not_available:register:" + ИмяРегистра);
		Возврат ОшибкаСклад("register_not_found", Предупреждения);
	КонецЕсли;

	// 3. Разыменование навигационных ссылок. ar_Утилиты.ОбъектИзНавигационнойСсылки
	// не бросает исключение при некорректном формате, а возвращает Неопределено.
	СсылкаНоменклатуры = ar_Утилиты.ОбъектИзНавигационнойСсылки(СтрокаНоменклатуры);
	СсылкаСклада = ar_Утилиты.ОбъектИзНавигационнойСсылки(СтрокаСклада);

	Если Не ЗначениеЗаполнено(СсылкаНоменклатуры) Тогда
		Возврат ОшибкаСклад("nomenclature_not_found", Предупреждения);
	КонецЕсли;
	Если Не ЗначениеЗаполнено(СсылкаСклада) Тогда
		Возврат ОшибкаСклад("warehouse_not_found", Предупреждения);
	КонецЕсли;

	// 4. Запрос к виртуальной таблице Остатки. Значения передаются только через
	// УстановитьПараметр (Номенклатура, Склад), без конкатенации в текст запроса.
	// Имя регистра подставляется в текст запроса прямой конкатенацией: оно приходит
	// не от LLM, а от ar_ToolDispatcher.ИмяОбъектаМетаданных и уже проверено выше
	// через Метаданные.РегистрыНакопления.Найти, поэтому не является пользовательским
	// вводом и не создаёт риска инъекции.
	Попытка
		Запрос = Новый Запрос;
		Запрос.УстановитьПараметр("Номенклатура", СсылкаНоменклатуры);
		Запрос.УстановитьПараметр("Склад", СсылкаСклада);
		Запрос.Текст =
			"ВЫБРАТЬ
			|	Остатки.КоличествоОстаток КАК Количество
			|ИЗ
			|	РегистрНакопления." + ИмяРегистра + ".Остатки(
			|		,
			|		Номенклатура = &Номенклатура
			|			И Склад = &Склад) КАК Остатки";

		Выборка = Запрос.Выполнить().Выбрать();
	Исключение
		Возврат ОшибкаСклад("query_failed", Предупреждения);
	КонецПопытки;

	Количество = 0;
	Если Выборка.Следующий() Тогда
		Количество = Выборка.Количество;
	КонецЕсли;

	Результат = Новый Структура;
	Результат.Вставить("nomenclature", ar_Утилиты.НавигационнаяСсылкаОбъекта(СсылкаНоменклатуры));
	Результат.Вставить("warehouse", ar_Утилиты.НавигационнаяСсылкаОбъекта(СсылкаСклада));
	Результат.Вставить("quantity", Количество);
	Результат.Вставить("warnings", Предупреждения);

	Возврат ar_JSON.ВЗначениеJSON(Результат);

КонецФункции

// Разбирает JSON-строку аргументов tool в Соответствие.
//
// Параметры:
//  АргументыJSON - Строка - JSON-объект аргументов от LLM.
//
// Возвращаемое значение:
//  Соответствие - разобранные аргументы; Неопределено при пустом входе или
//  ошибке парсинга JSON.
//
Функция ДесериализоватьАргументыСклад(Знач АргументыJSON)
	Если ТипЗнч(АргументыJSON) <> Тип("Строка") Или ПустаяСтрока(АргументыJSON) Тогда
		Возврат Неопределено;
	КонецЕсли;
	Попытка
		Возврат ar_JSON.ИзJSON(АргументыJSON);
	Исключение
		Возврат Неопределено;
	КонецПопытки;
КонецФункции

// Читает значение поля из Соответствия аргументов с дефолтом при отсутствии.
//
// Параметры:
//  Коллекция - Соответствие - разобранные JSON-аргументы.
//  Ключ      - Строка - имя поля.
//  Дефолт    - Произвольный - значение при отсутствии поля.
//
// Возвращаемое значение:
//  Произвольный - значение поля или Дефолт.
//
Функция ЗначениеИзКоллекцииСклад(Знач Коллекция, Знач Ключ, Знач Дефолт)
	Если ТипЗнч(Коллекция) <> Тип("Соответствие") Тогда
		Возврат Дефолт;
	КонецЕсли;
	Значение = Коллекция.Получить(Ключ);
	Если Значение = Неопределено Тогда
		Возврат Дефолт;
	КонецЕсли;
	Возврат Значение;
КонецФункции

// Формирует JSON-строку ошибки-observation с warnings.
//
// Параметры:
//  КодОшибки      - Строка - машиночитаемый код ошибки.
//  Предупреждения - Массив - список строк warnings, может быть пустым.
//
// Возвращаемое значение:
//  Строка - JSON вида {"error":"<код>","warnings":[...]}.
//
Функция ОшибкаСклад(Знач КодОшибки, Знач Предупреждения)
	Объект = Новый Структура;
	Объект.Вставить("error", КодОшибки);
	Объект.Вставить("warnings", Предупреждения);
	Возврат ar_JSON.ВЗначениеJSON(Объект);
КонецФункции

ПРИМЕЧАНИЕ. Логическое имя "ОстаткиНоменклатуры" — придуманное для этого примера.
Согласуйте свои логические имена с тем, что уже используется в регистре сведений
ar_ПереопределенияОбъектов на целевой базе, чтобы не плодить дубли одного и того
же понятия под разными именами.

Функция Диспетчер(ИмяПроцедуры, Аргументы, Контекст) в ВашПрефикс_ToolСклад:

перед маркером-комментарием в ВызватьПользовательскийТул, и (см. раздел 4.2,

================================================================================
  ИТОГ
================================================================================

1. Свой tool — это свой общий модуль в вашем оверлее src/ + одна ветвь в
   ar_ToolПереопределяемый, не патч ar_ToolDispatcher/ar_ToolCRM и других
   ядровых модулей по существу (раздел 2).
2. Сигнатура tool-функции и контракт DryRun/IdempotencyKey/approval —
   обязательны для любого mutating tool (раздел 3).
3. Подключение к диспетчеру — через переопределяемый модуль
   ar_ToolПереопределяемый.ВызватьПользовательскийТул (одна ветвь ИначеЕсли на
   каждый ваш общий модуль) — рабочий, не временный путь (раздел 4).
4. Универсальность достигается двумя indirection-фасадами: ИмяОбъектаМетаданных
   (объекты) и ar_МаппингМетаданных.ИмяРеквизита (реквизиты, ТОЛЬКО ДЛЯ ЧТЕНИЯ) —
   плюс проверкой наличия перед обращением и warnings вместо ошибок (раздел 5).
5. Запись типовых документов — не маппинг, а адаптер ar_АдаптерЗаполнения под
   конкретную конфигурацию (раздел 6).
6. Режим «Код» — не для распространяемых tools; всегда режим «Процедура» +
   собственный общий модуль (раздел 7).
