# Политика безопасности

AgentRunner даёт языковой модели доступ к данным рабочей информационной базы
1С. Это создаёт риски, которых нет у обычного расширения, поэтому прочитайте
этот документ до установки в продуктивный контур.

---

## Сообщить об уязвимости

**Не открывайте публичный issue для уязвимостей.**

- GitHub Security Advisory: вкладка **Security → Report a vulnerability**
  в репозитории `AI-1C-Expert/agentrunner` — предпочтительный канал.
- Если недоступно — issue с меткой `security` **без технических деталей**,
  только с просьбой связаться.

Что приложить: версию расширения (`ar_ВерсияРасширенияБД`), версию платформы
и конфигурации, шаги воспроизведения, оценку последствий.

**Сроки:** подтверждение получения — 5 рабочих дней; первичная оценка — 14
дней; исправление критичных проблем — по возможности в ближайшем релизе.
Проект развивается силами одного мейнтейнера, поэтому сроки ориентировочные,
а не договорные.

Мы не выплачиваем вознаграждение за найденные уязвимости.

## Поддерживаемые версии

Проект в стадии `0.x`: публичного релиза ещё не было, обратная совместимость
не гарантируется. Исправления безопасности выходят только для последней
версии. После выхода `1.0` политика будет пересмотрена (см. `MIG-07`).

## Модель угроз: что нужно понимать до установки

### 1. API-ключи хранятся без шифрования

Ключи LLM-провайдеров лежат в регистре сведений `ar_ХранилищеСекретов`
**в открытом виде**. Платформенное `БезопасноеХранилище` в расширении
недоступно: его `ПередЗаписью` отклоняет запись из кода расширения
(«Действие недоступно в безопасном режиме»), а признак «Привилегированный»
для общих модулей расширений платформа не разрешает.

Защита обеспечивается **только правами доступа**: регистр сознательно не
упомянут ни в одном `Rights.xml`, доступ к нему получает лишь серверный код
модуля `ar_Secrets` через `УстановитьПривилегированныйРежим`.

**Из этого следует:** администратор ИБ и любой, кто имеет доступ к файлу
базы или её резервной копии, может прочитать ключи. Используйте ключи с
ограниченными правами и отдельным бюджетом, не переиспользуйте
production-ключи основной инфраструктуры.

### 2. Данные уходят внешнему провайдеру

При настроенном облачном провайдере (OpenAI, Anthropic, GigaChat, YandexGPT)
содержимое запросов и результаты вызова tools **передаются третьей стороне**.
Условия обработки определяются соглашением провайдера и вне контроля проекта.

Средства снижения риска:
- **Режим соответствия (Compliance)** — маскирует ПДн и секреты во всём
  отправляемом контексте: паспорт, СНИЛС, телефон, email, ИНН, а также
  API-ключи (`sk-…`, `ya29.…`, `Bearer …`). По умолчанию **выключен**.
- **Правила маскирования ПДн** (`ar_ПравилаМаскированияПДн`) — точечное
  сокрытие конкретных полей конкретных объектов.
- **Локальный провайдер** (LM Studio, Ollama и совместимые по OpenAI API) —
  данные не покидают периметр.

Для баз с персональными данными в смысле 152-ФЗ включайте Compliance-режим
или используйте локальную модель.

### 3. Модель может ошибаться и действовать нежелательно

LLM недетерминирована и подвержена prompt injection: данные из ИБ
(наименование контрагента, комментарий к документу) попадают в контекст и
могут содержать инструкции, влияющие на поведение агента.

Контуры защиты:
- **Очередь подтверждений** (`ar_ОчередьApproval`) — все изменяющие действия
  строят payload и ждут решения оператора. Tools не проводят документы сами.
- **Уровни риска**: `Read` → `Draft` → `Write` → `Commit`; порог, выше
  которого требуется подтверждение, настраивается.
- **Запрещённые объекты** (`ar_ЗапрещённыеОбъекты`) — чёрный список
  метаданных, недоступных агенту.
- **Лимиты** — максимум шагов и действий на запуск, потолок расхода токенов.
- **Аудит** — все запуски, вызовы tools и решения оператора пишутся в
  регистры `ar_Запуски`, `ar_СобытияЗапуска`, `ar_ДействияАгента`.

**Не отключайте подтверждения в продуктивной базе**, пока не убедились в
поведении агента на копии.

### 4. Права агента = права пользователя

Агент работает в правах пользователя, от имени которого запущен, и уважает
RLS. Отдельные роли расширения: `ar_РольЧитатель`, `ar_РольОператор`,
`ar_РольАдмин`, `ar_РольОчисткаAudit`, `ar_РольСлужебный`.

⚠️ **Поведение tools под ограниченными правами и RLS на момент публикации
не проверено полноценным тестом.** Не выдавайте агенту прав больше, чем
требует его задача, и проверьте выдачу на своих данных.

### 5. Сетевые вызовы

Обращения к LLM идут через `ar_HTTP`. Разрешённые адреса ограничиваются
константой `ar_LLM_AllowList_URL`. HTTP-сервисы расширения
(`ar_AgentsAPI`, `ar_RunsAPI`, `ar_HealthAPI`) при публикации базы в интернет
требуют аутентификации и ограничения доступа на уровне веб-сервера.

## Принципы, заложенные в код

- **Никаких `Выполнить()` / `Вычислить()`** в ядре и реализациях tools —
  модель не может выполнить произвольный код.
- **Привилегированный режим** — только там, где этого требует спецификация
  (аудит, хранилище секретов, запуск фоновых заданий), всегда парно
  с возвратом в обычный режим.
- **Секреты маскируются** во всех точках вывода: журнал, служебный лог,
  observation для LLM, аудит.
- **Изменяющие действия** проходят через очередь подтверждений.

## Установка: рекомендации

1. Сначала — копия базы, не продуктив.
2. Начните с локальной модели либо с ключа с ограниченным бюджетом.
3. Включите Compliance-режим, если в базе есть персональные данные.
4. Дайте агенту минимальную роль и проверьте выдачу tools.
5. Не отключайте очередь подтверждений, пока не увидели поведение агента.
6. Просматривайте `ar_СлужебныйЛог` и Run Viewer после первых запусков.
