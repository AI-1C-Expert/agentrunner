# Как участвовать в разработке

Спасибо за интерес к AgentRunner. Проект открыт для вкладов — от отчётов об
ошибках до новых tools.

---

## Быстрый путь

1. Обсудите замысел в issue **до** написания кода — так меньше шансов, что
   работа не подойдёт по архитектуре.
2. Форкните репозиторий, создайте ветку от `main`.
3. Внесите изменения, прогоните валидаторы (см. ниже).
4. Откройте pull request и подпишите [CLA](CLA.md) — бот подскажет как.

---

## Что нужно для работы

- **1С:Предприятие 8.3.26** и выше. Файловый режим для самой ИБ поддерживается,
  но целевой сценарий — клиент-серверный.
- Конфигурация на базе **БСП**. Глубоко протестирована только **БП 3.0**;
  УТ 11, ERP 2 и ЗУП 3.1 пока не проверены.
- Расширение ставится как `.cfe` в режиме «Расширения конфигурации».

Исходники хранятся XML-выгрузкой в `src/`. Собирать `.cfe` вручную для
разработки не нужно — загружайте `src/` в базу через конфигуратор
(`Загрузить конфигурацию из файлов`) или `ibcmd`.

## Соглашения по коду

Они не косметические: часть из них — требования безопасности.

### Именование
- Объекты метаданных — префикс `ar_` (задан в свойствах расширения).
- Общие модули — `ar_…` (например, `ar_ToolДокументы`). Исторические
  исключения `aosPersonalData*` сохранены ради совместимости; в новом коде
  используйте `ar_`.
- Роли — `ar_Роль…`.
- Идентификаторы tools для LLM — `snake_case` по-английски
  (`search_clients`, `create_invoice_draft`).

### Язык
- Код, комментарии, спецификации — по-русски.
- Пользовательские строки — только через `НСтр("ru='…'; en='…'")`.

### Жёсткие правила
- **Никаких `Выполнить()` и `Вычислить()`** в ядре и реализациях tools.
- **Привилегированный режим** — только там, где это обосновано (аудит,
  хранилище секретов, фоновые задания), обязательно парно:
  ```bsl
  УстановитьПривилегированныйРежим(Истина);
  Попытка
      // …
      УстановитьПривилегированныйРежим(Ложь);
  Исключение
      УстановитьПривилегированныйРежим(Ложь);
      ВызватьИсключение;
  КонецПопытки;
  ```
- **Секреты маскируются** во всех точках вывода — используйте
  `ar_Утилиты.МаскироватьСекреты` / `МаскироватьПДнВТексте`.
- **Изменяющие действия проходят через очередь подтверждений**
  (`ar_ОчередьApproval`). Tool формирует payload, но ничего не проводит.
- **Транзакции** — `НачатьТранзакцию` / `ЗафиксироватьТранзакцию` /
  `ОтменитьТранзакцию` парно внутри `Попытка`.
- Обращения к секретам — только через `ar_Secrets`. Прямая работа с
  `ar_ХранилищеСекретов` нарушает архитектурный контракт (см. `SEC-01`).
- **Лицензионная шапка AGPL-3.0** — в каждом `.bsl` (см. существующие файлы
  как образец).

### Переиспользование БСП
Прежде чем писать своё, поищите готовое в БСП: `ОбщегоНазначения`,
`ДлительныеОперации`, `РаботаСHTTPСервисами`, `Взаимодействия` и другие.
В комментарии укажите источник: `[Реф: БСП/CommonModules/…]`.

## Проверки перед pull request

Обязательный минимум:

```bash
# Структурная проверка расширения
python3 .claude/skills/cfe-validate/scripts/cfe-validate.py -ExtensionPath src

# Для изменённых объектов метаданных
python3 .claude/skills/meta-validate/scripts/meta-validate.py …

# Для изменённых форм
python3 .claude/skills/form-validate/scripts/form-validate.py …
```

Тот же `cfe-validate` выполняется в CI на каждый push и pull request.

⚠️ **Валидаторы не ловят ошибки времени выполнения.** Необъявленная функция
или неверная директива компиляции проходят проверку, но падают при загрузке
в базу. Обязательно загрузите изменения в реальную ИБ и проверьте сценарий
руками.

При изменении `src/` **поднимайте версию** в `Configuration.xml` — она видна
в служебном логе и позволяет убедиться, что правка доехала до базы.

## Как добавить свой tool

1. Реализуйте функцию в подходящем модуле `ar_Tool…` (или создайте новый).
2. Опишите манифест в формате OpenAI function calling — посмотрите, как это
   сделано у соседних tools в том же модуле.
3. Зарегистрируйте tool в `ar_ToolDispatcher`, включая человекочитаемое
   представление и категорию.
4. Задайте `RiskLevel`: `Read` → `Draft` → `Write` → `Commit`. Всё, что
   меняет данные, обязано проходить через очередь подтверждений.
5. Проверьте живьём в диалоге с агентом на копии базы.

Если tool специфичен для вашей конфигурации, рассмотрите точку расширения
`ar_ToolПереопределяемый` — она позволяет не трогать ядро.

## Оформление pull request

- Одна логическая задача — один PR. Не смешивайте рефакторинг с фичей.
- В описании: что меняется, зачем, как проверялось (на какой конфигурации и
  версии платформы).
- Не коммитьте `AgentRunner.cfe`, содержимое `1C_DB/` и файлы с ключами.
- `ConfigDumpInfo.xml` меняется автоматически при выгрузке — это нормально.

### Стиль коммитов
Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`.
Если есть ID задачи из `.docs/Tasks.md` — укажите его:
`fix(PII-07): восстановить маскирование телефонов`.

## Лицензия вклада

Проект распространяется под **AGPL-3.0**. Отправляя pull request, вы
соглашаетесь с условиями [CLA.md](CLA.md): авторские права остаются за вами,
а проект получает право использовать вклад, в том числе в коммерческих
слоях. Ядро при этом остаётся под AGPL-3.0 — это зафиксировано в CLA как
встречное обязательство.
